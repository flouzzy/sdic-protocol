## Abstract

This RFC proposes a standardized data structure for the "Action Ledger" within the SDIC-1 framework to facilitate multi-agent synchronization. The Action Ledger provides a strict, append-only, cryptographically verifiable record of AI intentions. This ensures that in a multi-agent environment (Swarm Consensus), intentions from various autonomous agents can be deterministically ordered, validated, and synchronized without direct state mutation by any single agent.

## Motivation

As enterprise systems scale to incorporate multiple autonomous agents, the need for a shared, deterministically ordered mechanism for proposing state changes becomes paramount. Without a standardized Action Ledger, agents might propose conflicting actions, leading to non-deterministic state transitions and race conditions. By strictly standardizing this ledger, we enable a robust Swarm Consensus, ensuring that all proposed state mutations are immutably recorded, structurally validated, and deterministically executed.

## Specification

### 1. Feynman-Style Analogy

Imagine a busy restaurant kitchen. You have multiple chefs, each working on different dishes. If every chef just threw their ingredients into the pots on the stove whenever they felt like it, the meals would be ruined. Instead, they use a ticket rail.

When a chef wants to cook something, they don't immediately start cooking. They write exactly what they want to do on an order ticket and place it on the rail. The head chef looks at the tickets one by one. The head chef checks if the ticket is written in the correct format and if the ingredients are available. If everything is correct, the head chef gives the command to actually cook the dish. All chefs can see the ticket rail, so they know what everyone else is proposing and can adjust their own plans accordingly.

### 2. Technical Mapping

In our technical architecture, the components of the analogy map directly to the SDIC-1 architecture:

* **The Chefs (Agents):** These represent the independent autonomous AI agents operating within their isolated sandboxes. They compute what action they believe should happen next based on their context.
* **The Pots on the Stove (System State):** This is the actual application database and state. Agents have no direct access to modify this.
* **The Ticket Rail (The Action Ledger):** This is the standardized, append-only ledger where agents submit their intentions. It serves as the single source of truth for all proposed state changes.
* **The Order Ticket (Semantic Intent):** This represents the JSON payload generated by the agent, cryptographically signed and adhering to a strict schema.
* **The Head Chef (Host Application / Validator):** This is the deterministic control layer that sequentially processes the ledger, validates the schemas, verifies cryptographic signatures, and executes the state transitions.

### 3. JSON Schema Definition

The Action Ledger entry must strictly adhere to the following JSON Schema. Every agent intention must be encapsulated within an `intent_proposal`. To enforce zero-trust schema validation, `"additionalProperties": false` is strictly set.

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "ActionLedgerEntry",
  "type": "object",
  "properties": {
    "transaction_id": {
      "type": "string",
      "format": "uuid"
    },
    "timestamp": {
      "type": "string",
      "format": "date-time"
    },
    "agent_id": {
      "type": "string",
      "pattern": "^[0-9a-fA-F-]{36}$"
    },
    "intent_proposal": {
      "type": "object",
      "properties": {
        "action_type": {
          "type": "string"
        },
        "payload": {
          "type": "object",
          "additionalProperties": false
        }
      },
      "required": ["action_type", "payload"],
      "additionalProperties": false
    },
    "cryptographic_signature": {
      "type": "string"
    }
  },
  "required": [
    "transaction_id",
    "timestamp",
    "agent_id",
    "intent_proposal",
    "cryptographic_signature"
  ],
  "additionalProperties": false
}
```

### 5. Multi-Agent Synchronization Algorithm

The synchronization follows a strict deterministic algorithm for consensus:

1. **Intent Emission**: Agent $A_i$ computes an intent $I_i = C(X_i)$ based on its local context $X_i$.
2. **Canonical Hashing**: The agent creates a canonical JSON representation of $I_i$, denoted $I_{canon}$.
3. **Signing**: Agent $A_i$ generates signature $\sigma_i = Sign_{PrivKey_i}(Hash(I_{canon}))$.
4. **Submission**: $A_i$ submits $\{I_i, \sigma_i\}$ to the Action Ledger.
5. **Sequential Validation**: The Host System reads pending entries in temporal order. For each entry $E$:
    1. Verify $\sigma_i$ against $A_i$'s Public Key.
    2. If signature is invalid, reject $E$.
    3. Verify Schema: $V(I_i)$. If $V(I_i) = 0$, reject $E$.
    4. Evaluate Business Logic (Consensus constraints).
6. **State Execution**: If step 5 passes, transition system state $S_{t+1} = E(S_t, I_i)$.
7. **Rehydration**: All agents pull the updated state $S_{t+1}$ from the ledger to refresh their context.

## Rationale

This design ensures that multiple agents cannot create race conditions on the deterministic host system. By forcing all agents to write cryptographically signed proposals to an append-only ledger, the host system maintains absolute authority over the sequence and validity of state transitions. The strict JSON schema guarantees semantic determinism, rejecting any hallucinatory or malformed payloads before they reach the execution engine.

## Backwards Compatibility

This RFC introduces a new schema standard for multi-agent environments. It is fully backwards compatible with single-agent systems implementing v1.0.0-draft, as a single-agent system is functionally a multi-agent system with only one participant writing to the ledger.

## Security Considerations

To prevent relabeling or replay attacks, the cryptographic signature must be computed exclusively over the canonical representation of the entire entry (excluding the signature field itself). The inclusion of the `transaction_id` (UUIDv4) and `timestamp` guarantees cryptographic freshness for each submission.
